# 首版任务工程设计

状态：2026-09-16 用户已批准。首阶段后台导出已实施并验证；生成服务、候选采用、费用结算和多人部署仍未实施。下文保留完整目标设计，以下实施记录区分实际能力。

## 首阶段实施记录

- 六张任务表及迁移版本 3 已实施；tasks 另保存 progress、total、export_id，用于单任务导出进度和既有 exports 的唯一关联。实际数据库已备份后迁移。
- 已接通提交、列表分页、详情、取消排队、恢复导出。暂时只接受 operation=export；copy/image 明确返回未接入且不建任务。产物采用接口及套图 artifact 引用留待真实生成服务阶段，不允许当前伪造生成产物。
- worker 由业务服务启动为独立进程，并发 1；租约 60 秒、心跳 15 秒。父进程断开后不再领取新任务；执行中断的本地任务在租约过期后恢复。未设置自动供应商重试或切换。
- 一次任务按页保存文件与哈希；ZIP 用当前依赖 fflate 的 Zip/ZipPassThrough 按 64KB 读取写出，写入等待后才读下一块。每页渲染使用 Sharp 异步处理。恢复验证文件哈希；失败恢复使用原 exportId。
- 未完成旧同步导出只在版本迁移时标为失败；普通 Store 打开不修改任务。历史下载保持有效，旧同步提交入口已撤下。
- 29 项测试已通过，其中故障注入只用于测试。真实独立 worker 在测试隔离目录完成导出；没有向用户数据库灌入测试商品。浏览器连接不可用，点击验收未完成。
- 以下仍为后续要求：候选采用、完整生成参数/配置校验、费用预留结算、供应商状态核实、图片产物引用、市场查询优化。不能把建有表解释为这些业务已经可用。

## 1. 目标与当前差距

围绕“保存商品 → 确认页面规划与文案 → 提交制作 → 离开页面 → 返回处理部分失败 → 采用结果 → 审核导出”设计。首版使用单机业务服务和独立执行进程，不引入通用工作流、Redis、消息中间件、多租户或自动投流。

| 已有代码行为 | 下一阶段需要达到的行为 |
|---|---|
| 商品、套图不可变版本与 baseVersion 冲突检查 | 任务引用固定版本；采用结果也检查版本，不覆盖编辑 |
| exports 有 running/succeeded/failed 记录，请求内串行处理 | 请求快速返回任务，worker 持久执行；页面关闭不影响执行 |
| Store 构造时将 running 导出标记失败 | 移除构造期批量改状态，交给租约恢复；第二进程启动不能误伤正在运行任务 |
| 图片先写文件后登记，无持久恢复流程 | 暂存、最终文件、数据库登记按阶段可核对恢复 |
| 外部能力返回未配置，无真实调用 | 协议核实、固定能力配置、明确计费和不确定结果处理后才开放 |
| React 页面 useState，fetch 只抛 message | 服务端任务为事实来源；保留结构错误和 requestId，按版本刷新 |
| 市场研究批次列表全量、候选逐条读取 | 列表分页与批量查询；保持同批次口径，不能靠缓存掩盖查询成本 |

## 2. 业务边界与执行单元

文案、图片、导出是三个明确操作，不做一键跨过确认的隐式流水线。文案产物为候选，每页带事实引用；采用后仍需确认。图片任务使用确认文案和素材；任务成功不自动采用，更不自动审核。导出只能提交已审核且引用最新商品资料的整套设计稿。

job 是一次用户提交，task 是一个可独立处理的执行单元。文案和图片按页建 task；整套导出建一个 task，保存已完成页的文件清单。17 张图某两页失败时，保留其余结果。首版不建立通用 DAG 或任意父子任务树。

采用结果是显式写操作：检查原输入对应的商品版本仍有效、设计稿 baseVersion 未变、产物页与目标一致，再创建新版本。商品资料已变化时阻止直接采用，提示重新核对并用当前资料提交；不自动移植旧结论。仅其他页编辑造成版本冲突时，刷新后用户可再次选择采用，不能自动覆盖。

## 3. 状态与转移

任务执行状态与页面审核分离。现有 reviewed 字段继续承担“该版本页面已确认”，不在本轮扩展部门审批系统。未通过资料或排版检查的页面属于待完善；生成成功页属于候选，采用后为待审核。

| 状态 | 含义 | 允许的后续 |
|---|---|---|
| queued | 已持久保存，未领取 | running、cancelled |
| running | 领取成功，本地处理或准备请求 | waiting_external、saving_result、failed、needs_reconciliation |
| waiting_external | 已确认供应商接受，具备查询标识 | waiting_external、saving_result、failed、needs_reconciliation |
| saving_result | 已有可恢复的结果描述，校验与保存产物 | succeeded、failed、needs_reconciliation |
| needs_reconciliation | 不能确认外部接受、完成或费用状态 | 根据查询证据进入 waiting_external、saving_result 或 failed；不能直接 queued |
| succeeded | 产物文件和记录已确认提交 | 终态，不能改写结果 |
| failed | 明确失败；errorCode 和 recoveryAction 指明是否可恢复 | 仅允许安全本地恢复或只读查询恢复；新的付费生成必须新 job |
| cancelled | 未领取前已取消 | 终态 |

job 状态从所有 task 推导，不另外写一份可能冲突的状态：全部成功为 succeeded，全部取消为 cancelled，全部失败为 failed；仍有执行任务为 active；无执行任务但存在待核实为 needs_reconciliation；其他终态混合为 partial。界面同时显示各状态数量，不用单一百分比掩盖问题。

队列取消与领取用短写事务互斥。已领取不能声明已取消；批量取消返回明确剩余项。没有供应商取消协议时不提供“停止外部生成”。失败任务不能仅按 HTTP 状态或租约超时盲目重新生成。

## 4. 输入快照与内部接口

提交前先保存套图。服务端在同一短事务校验 kitVersion、productVersion、pageIds、素材归属、已确认文案、能力配置、参数及配额，创建 job/tasks 与预算预留。任何一项失败整批不创建。接口细节见 [接口契约](04-api-contracts.md)。

job 输入快照包括商品与套图版本、页面内容、素材 ID 与哈希、模板/提示词版本、provider/model/profileVersion、规范参数和输出规格。不能只存可变化的最新配置引用。凭证值不入快照；配置只存环境变量名称与固定供应商配置标识。执行时凭证缺失明确失败，不能自动换供应商或模型。

Idempotency-Key 由前端一次用户动作生成并保留至收到明确结果。响应丢失后重发原键；新生成新键。服务器存规范输入哈希。同键同输入取回原任务；不同输入冲突。内部幂等不等于供应商 exactly-once。

## 5. 拟新增数据结构（尚未批准）

| 表 | 核心字段和约束 |
|---|---|
| jobs | id、kit_id、kit_version、product_id、product_version、operation、input_snapshot、profile_snapshot、created_at；版本复合外键指向既有版本表，快照不可变 |
| tasks | id、job_id、page_id（导出可空）、ordinal、state、stage、version、lease_owner、lease_until、lease_epoch、next_run_at、recovery_action、error_code、safe_message、created_at、updated_at；UNIQUE(job_id,ordinal)；领取索引(state,next_run_at,created_at) |
| task_attempts | id、task_id、sequence、lease_epoch、phase、provider_request_id、provider_job_id、response_descriptor、started_at、finished_at、safe_error；UNIQUE(task_id,sequence)；描述仅保存恢复必需字段 |
| artifacts | id、task_id、output_key、kind、relative_path、sha256、mime、bytes、validated_data、created_at；UNIQUE(task_id,output_key)；JSON 文案存 validated_data，图片/ZIP 使用私有文件；引用产物检查 task.job 的商品归属 |
| operation_keys | scope、key、request_hash、resource_id、created_at；PRIMARY KEY(scope,key)，覆盖提交、恢复、采用；保存明确操作结果引用 |
| usage_ledger | id、task_id、attempt_id、event_key、entry_type、amount_minor、currency、quantity、unit、price_version、cost_status、created_at；UNIQUE(event_key)；预留/释放/结算追加记账，未知费用不能写 0 |

不改变 assets 的原图含义：原始上传仍存 assets，生成候选存 artifacts。套图 page 输入需要显式支持“原始素材或生成产物”的互斥引用；该契约变更须同步更新预览、审核、导出、历史恢复和前端，不能将生成文件伪装为用户上传。旧版本保留原 schema 解码，不迁移重写旧设计 JSON。

既有 exports 表继续保存交付历史。新导出 task 通过稳定 output_key 及固定 exportId 建立一对一关系；登记成功文件、artifacts、exports 和 task 成功必须一个事务完成。旧同步入口统一替换，不同时运行两套执行方式。

## 6. 领取、并发与崩溃恢复

API 和 worker 是两个进程，使用同机 SQLite 和文件目录。数据库事务只处理记录，不在事务内等待网络或图片渲染。任务表就是首版队列，不进行“数据库提交后另发队列消息”，避免双写丢失。

首轮运行参数建议：本地导出并发 1、生成并发 1；轮询领取 1 秒、租约 60 秒、心跳 15 秒。均为待压测的内部初值，不代表供应商配额。图片渲染必须在不会阻塞心跳的执行环境中进行，禁止同步打包长期阻塞执行进程。

领取使用 BEGIN IMMEDIATE：筛选 next_run_at 到期且 queued 的任务，检查配置的全局并发/未决外部请求占额，更新 running 与 lease_epoch，再提交。心跳、结果提交和阶段更新必须带 taskId、owner、epoch 条件；旧执行者不能覆盖新代次。外部未决任务继续占供应商执行额度，租约失效不等于外部调用结束。

请求前先提交 attempt.phase=dispatching，再发网络请求。若此时崩溃，无法判断是否已发送，进入 needs_reconciliation；这是宁可留待核实也不重复扣费的边界。供应商具备经过验证的幂等键或按客户端标识查询能力时按其协议恢复，否则不自动重发。

确认接受后尽快保存 providerJobId；同步返回完成也先持久化恢复描述，再保存图片。恢复时优先查询或下载既有结果。带签名的临时下载 URL 不进普通日志/前端；若协议只能提供此类地址，确定安全存储方式前该恢复能力不能标为支持。

明确本地瞬态读写失败可有限恢复，建议最多 3 次、间隔 2/10/30 秒，记录每次结果。参数错误、无权限、磁盘满、内容无效不盲目重试。外部查询频率、429 等待与调用超时取决于核实后的协议，不在这里编造统一供应商规则。

## 7. 文件与数据库一致性

执行单元在私有 staging 目录写 attempt/产物编号对应文件；完成写入、刷盘、校验真实格式/大小/尺寸/哈希后，在同一卷移至不可覆盖的最终编号路径。最后事务登记 artifact 和任务成功。数据库成功前不对外返回可交付结果。

文件和数据库不是原子事务，恢复必须覆盖：暂存半文件不交付；最终文件存在而记录缺失时，依据持久 attempt、固定 output_key 与哈希重新登记；已登记但文件缺失时报告产物不可读取，不能重新付费生成来掩盖丢失。租约旧代次写出的文件不准登记，保留为待核对孤立文件；未经批准不自动删除。

导出按页生成到工作目录并记录清单，重启后对已完成页校验哈希再复用；不能将全部 PNG 长期堆在内存里。ZIP 采用有界/流式实现，库与接口在实施前核实。导出重试复用相同 exportId，旧下载记录不变。

## 8. 前端状态和缓存

服务端状态：商品资料、版本、任务、费用与审核，以数据库为准。编辑状态：当前草稿、选中页、未保存标识。界面状态：弹窗、筛选、分页。三者分开，不用任务响应覆盖 draft。

保留现有 React 状态方式，抽出领域 hook 管理请求和版本；暂不为此引入全局状态库。查询按资源编号与版本区分，过期响应丢弃或 AbortController 取消。离开页面提示未保存编辑；返回任务从服务端恢复。打开任务时每 2 秒查询，页面隐藏降为 10 秒，终态停止；离线显示连接中断，不把任务当失败；恢复网络重新读取。

缓存只做两处：不可变版本/图片按版本或内容哈希缓存；同次导出的素材缩放结果复用（现有实现已有）。商品最新版本、任务状态、审核结论、费用及核对列表不持久缓存。业务写成功后刷新关联查询。私有图片不能标记 public 缓存；含敏感字段不进入浏览器持久存储。

市场研究先用分页、批量读取核对记录、候选查询索引解决全量扫描；新增索引属于下一次 schema 评审，不能借缓存解决无限增长。CSV 现有每批 500 行校验保持同步，不全部改造成异步任务。

## 9. 费用、能力与安全边界

用户看到可理解的任务数量和费用口径，开发信息留在设置或诊断中。每个可用能力明确 provider/model、参考图支持、尺寸限制、查询与幂等支持、计价单位。具体官方协议尚未核实，首轮不选择供应商，不声称任意 OpenAI 格式兼容。

可可靠计算上限的配置，在创建 tasks 时同事务检查预算并逐任务预留；跨 worker 共用账本，不用内存余额。只有明确未产生收费的失败/取消才释放预留；结果未知继续占额。实际账单与预估分开，结算 event_key 防重复；币种不能直接相加。不能得到可靠计费上限的能力只显示估算及数量限制，禁止向用户承诺硬货币上限。

供应商返回结构先校验，文案引用只能指向输入事实；结构合格仍不能代替人工语义确认。下载只接受已核实供应商域名和协议，重定向/解析地址也检查，限制体积和时间；不允许传入任意 URL 让服务端抓取。

本轮仍单用户回环访问；填写“确认人”不等于认证。若进入多人企业部署，账号与权限、服务端商品/产物授权、审计和部署方案必须单独完成后才开放网络访问。

## 10. 日志、备份与验收

记录 requestId/jobId/taskId/attemptId、阶段、耗时、错误码，不记录密钥、完整商品请求或供应商原始响应。队列积压、未决请求、失败与保存失败从数据库查询，不新增遥测服务。操作界面显示可处理的错误与恢复动作。

完整备份：暂停新任务领取并等待文件写入/事务结束，备份 SQLite 与素材/产物目录并生成哈希清单，再恢复领取；更简单的首版运维方式是停服务及 worker 后备份整个 .runtime。只备份 SQLite 不称为完整恢复。恢复到隔离目录检查关联文件、任务状态、下载与历史，不使用真实付费接口做恢复测试。

| 故障场景 | 必须观察到的结果 |
|---|---|
| 连点提交 / 202 响应丢失 | 同键只有一组 job/tasks 和一次预算预留；不同输入冲突 |
| 提交后商品改变 | 任务仍按旧输入执行；采用时阻止混用新商品资料 |
| 17 页中 2 页明确失败 | 15 个产物保留，失败页独立呈现，不自动重做整套 |
| 外发后超时且无可查询标识 | 待核实、占额、不自动重发 |
| 租约过期及旧进程迟到 | 旧 epoch 不能提交结果；未决外部任务不重复发送 |
| 文件完成后数据库提交失败 | 从同一文件恢复登记，不重新生成 |
| 队列取消和领取同时发生 | 只有一方成功；不能既显示取消又发出调用 |
| 预算只够一个任务而并发提交两份 | 至多一份预留成功，另一份明确拒绝 |
| 重新打开 / 网络恢复 / 浏览器后台 | 读取真实任务状态，不丢已保存结果，不覆盖编辑草稿 |
| 导出到第 8 页中断 | 恢复后复用校验通过的页，最终 ZIP 仍对应固定版本 |
| 实际数据库迁移失败 | 整体回滚并保留迁移前备份；原商品、历史稿及下载可读 |

表中均为未来验收要求，不代表已经通过。代码实施需类型检查、业务/集成测试、真实浏览器流程；供应商联调另列，测试替身只用于故障注入。

## 11. 实施顺序与批准边界

1. 评审本文件及 API 契约，确认六张任务表、已有导出关联及套图产物引用的具体变更范围。
2. 获批后先以真实本地 PNG/ZIP 导出实现队列、worker、状态查询、幂等、恢复和前端进度；不需要模型 Key。
3. 核实一个文字及一个图片供应商官方协议，确认账户能力、计价、恢复和参数；再评审凭证配置，接入真实调用并完成文案/图片产物采用与审核。
4. 跑完整另一商品的制作交付，并对照故障矩阵验收。保持包装开发、自动投流与 AI 主播在首版之外。

此次没有建表、修改凭证或新增依赖。设计审核不能代替供应商实测；不可查询的外部不确定结果和人工审美判断不会被工程机制消除。
